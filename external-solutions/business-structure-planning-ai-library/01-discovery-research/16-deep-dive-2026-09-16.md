## Architecture patterns worth importing

### 1. Human-readable company layer + machine-executable agent layer

The Company OS repository separates documentation/handbook material from agent definitions and orchestration. This is a strong pattern for Nivy: humans should be able to understand the operating model while agents consume structured instructions.

### 2. Department-as-a-module

Each department should have a predictable package:

- purpose
- responsibilities
- goals/KPIs
- roles
- processes
- SOPs
- inputs/outputs
- tools
- agents
- skills
- workflows
- approvals
- knowledge sources
- templates
- audit/evidence

This makes departments reusable across Nivy brands.

### 3. Goal → plan → work → approval → evidence

The newer Company OS projects consistently treat company work as an execution loop rather than a prompt collection. Nivy should preserve this distinction.

### 4. Agents are workers, not the operating model

A useful Company OS needs policies, decision rights, process definitions, data/knowledge, workflows and governance around the agents. Simply collecting agents will create another tool pile.

### 5. Reusable agent packs

Instead of creating one giant Nivy agent, package agents by function and workflow. Example:

`Marketing → Research → ICP Research Agent → Content Brief Agent → SEO Agent → Distribution Agent → Analytics Agent → Review Agent`

### 6. Approval gates

High-impact actions should have explicit human approval gates, particularly:

- spending
- legal commitments
- tax/accounting submissions
- hiring/firing
- customer refunds
- external publishing
- production changes
- contractual commitments
- sensitive data access

## Nivy adoption sequence

1. **Mine Company OS / OPOS / BOS-AI / Autonomous Business OS** for structure.
2. Compare their department schemas against the existing Nivy Raw Repository taxonomy.
3. Extract reusable agent/skill/process patterns rather than copying entire repositories.
4. Map each candidate into `framework → process → SOP → template → skill → agent → workflow → system`.
5. Identify overlaps with existing Nivy work.
6. Select only the smallest reusable components needed for the first revenue engine.
7. Build custom components only where no credible reusable solution exists.

## Important evidence

The Company OS repository describes itself as an industry-agnostic operating system with a human handbook side and an AI workforce side, including 20 departments and 107 agent specifications. This makes it particularly relevant as an architectural reference, not automatically as something to deploy unchanged.

OPOS takes a different approach: the company itself is represented as versioned Markdown in Git, with Claude Code supplying native agent/skill primitives and human oversight through reviewable changes.

Autonomous Business OS demonstrates another useful pattern: workflows spanning lead intake, qualification, onboarding, delivery, finance and knowledge, with approval-gated and auditable execution.

## Do not blindly reuse

These projects are active software/architecture projects, not standards. Before production adoption verify:

- license
- security
- dependency health
- maintenance activity
- credential handling
- data residency
- model/provider assumptions
- integration quality
- failure/retry behaviour
- human approval mechanisms
- auditability
- total cost
